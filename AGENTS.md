# CometScout: instructions for the coding agent (Claude Code or Codex)

> CometScout was called jobpilot until October 2026; old names still work for now (README.md, top). Use the new ones in everything you write for the user.

> **Changing CometScout's code** (a feature, a fix, a task from `docs/tasks/`)? Follow `DEVELOPMENT.md` and `ROADMAP.md` instead; the steps below are for setting CometScout up for a user.

You are helping a job seeker set up and run CometScout on their own server. The user has a Claude or ChatGPT subscription; CometScout calls that CLI for every model step. Everything personal lives in `profile/`, `settings.json` and `.env`, which are never committed.

**In an installed home** (this folder has `app/current`), the code runs from `app/current` and every command is `node cli.mjs ...`. The clone's own folders (`lib/`, `sources/`, `decoder/` and the rest) are left from the first install and are not used: never run `node <folder>/<file>.mjs` from them. If `node cli.mjs doctor` says the home's docs are older than the installed release, run `node cli.mjs update --refresh-home` and read this file again.

## When the user says "set me up" (onboarding)

Goal: the first useful result in one sitting, a real job decoded against their profile and a tailored CV for it, before anything optional.

**Rules for every turn. Follow them literally.**
- One question per turn. A turn may also ask for yes/no confirmations of what you just wrote, nothing else.
- Every write to `settings.json`, to `profile/` or to the `.env` instructions: show the exact change first (a diff, or the whole new file) and wait for the user's yes. Then write it, and nothing more.
- Change settings with `node cli.mjs settings set <key> <json-value> --dry-run`: it checks the change like `doctor` and prints the diff. Show that diff; after the yes, run the same command without `--dry-run`. Values are JSON: `true`, `3`, `'"18:00"'`, `'["product manager"]'`. Edit `settings.json` by hand only for a key `settings set` refuses as locked, and show the diff of that edit first.
- Secrets: the user types tokens into `.env` themselves. Never ask for a token in the chat; never read or print `.env`.

**Start here, every time (a resumed session too):** run `node cli.mjs onboarding-state` and continue from the step it names. Do not rely on what you remember from an earlier session.

**Connected through the MCP server instead of a shell?** When you have CometScout's MCP tools (`onboarding_state`, `doctor`, `settings_set`, `secrets_form`; README: Use it from an AI client), use them for these steps: `onboarding_state` names the next step, `doctor` replaces step 1's command, `settings_set` changes `settings.json` (call it with `dry_run: true` first, show the diff, write after the user says yes), and `secrets_form` gives the user a one-time link to type a token into the workspace on their own computer, so a secret never goes through the chat. Steps that write profile files or run commands on the server (the profile, the CV library, the first run, the timer) still need a shell there: tell the user exactly what to run. The `setup` prompt walks through the same steps.

1. **Check the machine:** run `node cli.mjs doctor`. Fix what it lists, in order. When there is no `settings.json` yet, say that you will copy `settings.example.json` to `settings.json`, wait for the yes, then copy it. Packages and the daily timer come from `bash deploy/install.sh` (it needs sudo once).
2. **Profile (`profile/profile.md`):** ask these questions in this order, one per turn. Write nothing until the last one is answered; then show the whole file in the structure of `profile.example/profile.md` and wait for the yes. Use their words; never add a fact they did not give.
   1. What is your name, as it should appear on a CV? (It becomes the first heading of `profile.md`; leave `candidate_name` in `settings.json` at null, so the name is read from there.)
   2. What is your current or last role, and how many years have you worked in this kind of role?
   3. What are you strongest at? Three to five things.
   4. Which degree do you have, and which languages do you speak, at what level?
   5. Which roles do you want next, and in which domains?
   6. What company size suits you?
   7. What is your pay floor (gross, per year or per month, with the currency)? It is the minimum you accept, never the figure CometScout asks for.
   8. Where do you live, where are you allowed to work, and do you want remote, hybrid or on-site work (and where)?
   9. When could you start (notice period)?
   10. What should never be shown to you (hard gates: languages you do not speak, industries, role types, places)?
   11. What must CometScout never claim about you (scope guards: things you did not do or did only in part)?
3. **CV library (`profile/cv-library.json`):** ask for their CV (paste or file). Turn each bullet into a library item with an id, keeping their wording; add one or two taglines and summaries built only from those bullets. Show the whole library and let them correct every line before you save it: this file is the only source of facts for the CVs CometScout builds. Education is optional: leave `education` out (or null) if they have none, or give a list for several entries. Certifications, courses and awards go in `awards`; set `awards_heading` (for example "CERTIFICATIONS") and mark the ones that must always appear with `"required": true`.
4. **Fact rules (`profile/fact-rules.json`):** one regex rule per scope guard, so an overclaim gets flagged (see the example file). Anchor each rule on the candidate's own verb, as in `(ran|owned|managed)[^.]{0,40}P&L`, never on the bare noun: a posting's own words ("P&L ownership") must not be flagged. Show the file and wait for the yes. Optional: `profile/lint-rules.json` holds banned claims (a CV that still carries one is not sent), warnings and word limits; whenever the user corrects a fact, offer to add a rule for it.
5. **Voice (`profile/voice.md`, optional but valuable):** ask for two or three texts they wrote themselves (not AI-written). Describe how they write in a short card and quote a few of their sentences as rhythm reference. If they want to measure the voice later (`node cli.mjs evals voice`), save those texts as `profile/voice-samples/*.md`. Optional too: `profile/eval-rubric.md`, their own criteria for "worth applying" shown on the labelling screen; draft it from `profile/profile.md` (wants, location, hard gates) in the shape of `profile.example/eval-rubric.md` and let them correct it.
6. **Sources:** ask each of these, in this order, one per turn. A "no" is an answer: never skip a question because the answer seems obvious.
   1. **Job boards:** "Which five to ten companies do you want to watch?" Find each company's public board. CometScout reads Greenhouse (`boards.greenhouse.io/<board>`), Ashby (`jobs.ashbyhq.com/<board>`), Lever (`jobs.lever.co/<board>`), Personio (`<board>.jobs.personio.de` or `.com`) and Gem (`jobs.gem.com/<board>`). A company on another system (Workday, SmartRecruiters, its own careers page): say so, and send its job links through the drop folder (question 4). Then ask for title and location filters, and set `sources.ats_boards` (dry run, diff, yes).
   2. **RealtimeJobs:** "Do you have a RealtimeJobs API token?" If yes: they put `RTJ_API_TOKEN=...` in `.env` themselves; enable `rtj`.
   3. **LinkedIn alerts:** "Do you get LinkedIn job alerts in Gmail?" If yes: they create a Google Cloud project with the Gmail API enabled and an OAuth client of type "Desktop app" (you can walk them through the console), put `GMAIL_CLIENT_ID` and `GMAIL_CLIENT_SECRET` in `.env` themselves, then run `node tools/gmail-auth.mjs` and sign in in their own browser (on a VPS: `ssh -L 8765:127.0.0.1:8765 <vps>` first). The token goes straight into `.env`; never read or print it. Enable `linkedin_alerts` and test with `node cli.mjs sources --only linkedin_alerts --dry-run --max-fetch 3`. Keep `max_fetch` and `delay_ms` modest: job pages are fetched from LinkedIn's public guest view, slowly, and the run stops by itself if LinkedIn throttles.
   4. **Other links:** "Are there other job links or boards you want CometScout to read?" If yes: enable `drop_dir` (its folder is `~/cometscout-drop`, created on the first run). Links go into a `*.queue.json` file there, `{ "candidates": [{ "title": "...", "url": "..." }] }`, and CometScout fetches each page (README: External producers (drop-dir)).
7. **First result:** first, the reset question. When `node cli.mjs doctor` lists decodes from the example profile, or the user tried the example profile before, ask: "You tried the example profile first. Shall I clear its results with `node cli.mjs reset --yes`? It deletes everything in data/ (queue, decodes, picks, packs, applications) and keeps the install's own state." Run it only after a yes. Then `node cli.mjs sources`, then `node cli.mjs decode --no-telegram`, then `node cli.mjs pack --no-telegram`. Show the picks and open the pack's PDF and `answers.md` with them (a salary question is left blank on purpose, with their floor and the posting's range as a note). This is the moment to fix the profile if a verdict or a CV line is off.
8. **Daily delivery:** Telegram: they create a bot with @BotFather and put `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` in `.env` themselves; set `delivery.telegram.enabled`. Ask what time they want the evening run, then on which days they want the digest (one question per turn); set `schedule` (`{ "days": [1, 2, 3, 4, 5], "time": "18:00" }`, ISO weekdays, 1 = Monday) and `timezone`. Before you run the timer, tell them when the first run will happen: `node cli.mjs timer --dry-run` prints it, and installing the timer never starts a run by itself. Then run `node cli.mjs timer`. With Telegram on, the timer also installs the bot (`/schedule`, `/time`, `/interview`), so they can change days and time from their phone later. If they put Telegram off, say that every digest is written to `data/digests` and goes on.
9. **Interview coach:** ask once, even if Telegram was put off: digests in `data/digests` count as delivery working. Do not list it as "optional, later"; ask the question. Explain in two sentences: the interview coach is a separate open-source Claude Code skill by Noam Segal (MIT, github.com/noamseg/interview-coach-skill) that helps them prepare for a company, practise answers, analyse an interview transcript and negotiate an offer; CometScout can install it next to itself and hand it their profile, CV, voice and applications so they do not tell their story twice. If they say no, move on. If yes, one step at a time:
   - run `node cli.mjs install-module coach`; it installs into `../interview-coach` unless they want another folder (`modules.coach.path`);
   - set `modules.coach.enabled` to `true` (say so in a sentence: doctor then checks the install);
   - run `node cli.mjs coach-handoff` and show them the file it wrote (`materials/cometscout-handoff.md` in the coach's folder); it is built only from their own files, with no tokens, job postings or packs;
   - tell them how to start it: `cd <coach folder> && claude`, then say `kickoff` and give it `materials/cometscout-handoff.md`. The coach needs Claude Code; `node cli.mjs doctor` shows whether `claude` is found. The evening run rewrites the file every day while `modules.coach.enabled` is true; `node cli.mjs coach-handoff` does it at once (for example right before an interview prep).
   - **Transcription (after the coach):** ask whether they record their interviews. If yes, run `node cli.mjs install-module transcribe` and set `modules.transcribe.enabled`. When their profile, their target roles or `locale` say Russian, ask once more: "Most of your interviews are in Russian? Then I can add GigaAM, a speech model that is much better on Russian (about 0.2 GB of CPU-only PyTorch to download, plus a 0.45 GB model on the first recording)." If yes, add `--with-gigaam` to the installer command. Mention `profile/glossary.txt` for the company and product names they use.
10. **Tell them the daily loop:** every evening they get up to two picks with a pack each; after applying, `node cli.mjs applied <company>` so picks move on; `node cli.mjs status <company> interview|rejected|offer` for news; `accepted` when they take an offer and keep looking.

## Rules
- Never invent facts about the user; the CV library and profile are theirs to approve.
- Never commit or print secrets. `.env` is chmod 600.
- Do not edit `profile.example/`; it is the public example.
- Prefer small, reversible changes to `settings.json`; explain each one in a sentence.
